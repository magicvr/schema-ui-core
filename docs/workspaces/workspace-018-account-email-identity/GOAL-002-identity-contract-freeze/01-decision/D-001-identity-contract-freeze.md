# D-001 · R1 账号邮箱身份合同冻结

## 背景

D-003 解冻后 R1 启动。I-001 / I-002 为 required、门禁 = R1 方案冻结（P-005）。2026-08-24 用户在裁决会话中书面选定三项细则：**投递形态 = 验证码**；**未校验地址 = 绑定即占槽**；**规范化 = 原样存储 + lower(email) 唯一**。VP-018 已冻结项（可空、换绑进波、非空唯一 fail-closed）作为既定前提投影入合同。

## 合同条款（冻结）

**§1 可空与登录**：`users` 持有单个可空 email 列；无邮箱账号照常登录；email 不是 mvp/dev 启动硬依赖。

**§2 绑定占槽**：发起绑定即写入该列并置 `pending`，地址随即占用唯一槽；他号对同址的绑定/换绑请求 fail-closed，失败语义可核对（`already_bound_or_pending`）。

**§3 唯一性与规范化**：展示保留用户输入原样；唯一性约束建在 `lower(email)` 上（PostgreSQL 表达式唯一索引 / SQLite 等价表达式索引）；应用层在比较与写库前做 trim + 大小写折叠归一。空值不参与唯一约束（多账号可为 NULL）。

**§4 校验投递形态**：6 位数字验证码，短时效、可重发（时效与冷却数值归 I-005，R3 接入前冻结）。校验信经 `kernel.MailSender` 投递，走 VP-017 现行渠道模型（默认渠道以当时配置为准）；dev/验收从 mock 出站记录取码，不锁历史 CaptureSink `Last()`。

**§5 换绑**：换绑 = 对同一单列的重新绑定——覆写为新地址并重置 `pending`，新址按 §2 占槽，旧址占用随覆写释放；新址验证通过后回到 `verified`。此条款为「单列 schema + 绑定即占槽」的机械推导（VP 冻结 users 单邮箱），不是独立产品裁决；若未来引入多邮箱/别名须重开本合同。

**§6 状态机**：三态 `unbound`（NULL）/ `pending` / `verified`。管理员代填是否允许保持待校验为 I-006（non-blocking），留 R3 裁决，不影响本合同。

**§7 运输与验收对齐**：身份面只消费 `MailSender` 端口，不感知供应商类型；R3/R4 验收对照 VP-017 当时默认渠道（预期 mock 出站记录）。

## 为什么

- 三项细则均有用户书面裁决，I-001 / I-002 门禁解除有据。
- 验证码使验收面最小且 mock 可检视；占槽消除「校验完成竞态」败方规则的必要性；lower 唯一是双方言可行标准解。

## 未选方案

- 魔术链接 / 双形态：实施面大，未被选定（用户裁决）。
- 仅已校验占槽：需额外定义冲突败方规则，未被选定。
- 强制小写存储：改写用户输入展示，未被选定。
