## 逐条核对

### a) A-001 required ×4 — genuine fixed

**F-001（P1）invite/accept 先验 token + 限流 — fixed**

- `PeekInviteToken`（`authsession/invites.go`）为 SHA-256 索引 SELECT；未知/过期/已用/已撤销一律 `ErrInviteInvalid`，无枚举面。
- 公开 accept（`handler/invites.go` `RegisterInviteAccept`）顺序：IP 滑窗 `allow` → Peek → 密码策略 → bcrypt → `AcceptInvite`。死 token 在 bcrypt 前返回。
- 限流：15 min / 10 次 / 容量 64K，key = `loginClientIP`；Peek 失败与 Accept 失败 `record`。比 A-001 建议的 20 次更紧。
- 接线：`composition.go` `RegisterInviteAccept(mux, authRepository)`。
- 回归锁：`TestInviteAcceptDeadTokenShortCircuitsBeforePasswordWork`、`TestInviteAcceptRateLimitBoundsUnauthenticatedSpray`。

**F-002（P2）disable / recovery-rotate 第二因子失败限流 — fixed**

- 共享 `mfaStepUpLimiter`（15 min / 5 次），key = `op|IP|userID`。
- 两端点均 `guardMFAStepUp` 后再调 service；仅 `ErrMFAInvalid` `record`；成功 `clear`；超限 429 `RATE_LIMITED` + `Retry-After`。
- `requireActiveSecondFactor` 仍是猜测面；限流把它从无界压到每操作 5/15 min。
- 桶为进程内 best-effort（与 login/changePassword 同模型；W12 单实例官方边界）。A-001「持久化 per-user 计数」未做，但不构成 required 未闭合。
- 回归锁：`TestMFAStepUpDisableAndRotateRateLimited`（两操作分桶、超限后合法码也 429、不吊销会话）。

**F-003（P2）enroll currentPassword 限流 — fixed**

- 同一 step-up 桶，`op=enroll`；`guard` 在 `VerifyPassword`（bcrypt）之前；错密 `record`，成功 `clear`。与 `account_self` `passwordLimiter` 5/15 min 同构。
- 回归锁：`TestMFAEnrollWrongPasswordRateLimited`。

**F-004（P2·bug）Confirm 匹配步进 — fixed**

- `Confirm` 取 `ValidateTotp` 的 `matchedStep` 写入 `SetLastUsedStep`，不再写 `now.Unix()/30`。

- 回归锁：`TestServiceConfirmPersistsMatchedStep`（注释写明旧代码必败）。
