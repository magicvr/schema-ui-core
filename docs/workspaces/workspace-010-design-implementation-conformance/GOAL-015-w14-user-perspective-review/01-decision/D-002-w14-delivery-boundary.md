# D-002 · W14 波次交付边界：审视 + 落盘，整改 deferred

> **⚠ 部分被用户裁决修正（2026-08-17，见 E-003/A-004）**：本文件「I-001 门禁移至未来整改波次」并把 S4 关门视为可放行的设定，被用户裁定为「绕过 P-004 用户裁决」——A-002（independent）的认可不构成用户裁决。**不实施整改**的边界本身与用户原始请求（「审视并落盘」）一致，仍成立；但 **I-001（F-01～F-14 的 in-scope/defer/优先级）恢复为本波关门 open required**，须用户书面裁决后 S4 方可关门。整改实施仍不在本波范围内。

## 决策

用户原始请求（2026-08-17）：「审视 api/web 已实现功能 → 找出并非很小的改进点 → **在工作区 10 新建子项目进行落盘**」。据此，本波（GOAL-015）交付物确定为：

1. **S1** 审视执行（E-001）——api/web 全量功能面走查 + 关键发现证据复核。
2. **S2** 台账与待决项落盘（D-001）——改进项 F-01～F-14（含文件:行证据、优先级、建议实施顺序、审计风险分级）+ 信息项 I-001/I-002 登记。
3. **S3** 独立交叉审计（A-002，grok-4.6 · reasoning high）——对 S1/S2 证据与「本波不实施整改」的成文诚实性做 independent 审核。
4. **S4** 台账同步与关门——审计响应 + goal-tree/workspace 更新 + git 提交 + 关门自审（A-003）。

**F-01～F-14 的整改实施一律 deferred**：不在本波执行，不静默决定 in-scope/优先级；I-001 门禁相应移至「未来整改波次」（P-005 deferred：延期理由 = 用户原始请求仅要求落盘；责任人 = 用户；下一复核触发 = 用户指示开始整改）。

## 为什么（取舍）

- **未选**：在本波内实施 F-01～F-14。理由：用户未指示实施；范围大、涉及 API/schema/安全/兼容语义，按 P-004/P-005 必须由用户裁决 in-scope/优先级与三个方案选择（F-01 handler 目录、F-04 通知本地化、F-08 调试框）。静默实施将违反裁决门禁。
- **未选**：把整改拆成多个子目标立即立项。理由：P-001——范围/优先级未裁决前属「尚不可直接执行」；应先留待用户裁决。

## 影响

- 本波只读/只写文档（docs/ 下治理台账与 goal-tree/workspace），不改任何业务代码。go 判定：无影响、不暂挂。
- F-01～F-14 台账保持可追溯（D-001），未来用户裁决后可直接作为整改波次的范围输入。
