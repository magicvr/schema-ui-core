## 1. 模块化单体 + 组合根（modular monolith with a static composition root）

| 1.1 | 模块化单体把「逻辑模块边界」与「单一部署单元」分开处理：代码按模块划分、模块只经 API 包对外暴露、内部包禁止被其他模块引用，整个应用仍编译并部署为一个进程/单元。 | ① Microsoft Learn · Common web application architectures — https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures（单体定义：行为自包含、核心在自己的进程内运行、通常作为单一单元部署；分层用于限制依赖方向）② Spring Modulith Reference · Fundamentals — https://docs.spring.io/spring-modulith/reference/fundamentals.html（application module = API 包 + internal 包，可用 `allowedDependencies` 显式声明允许依赖）③ Spring Modulith Reference · Verifying Application Module Structure — https://docs.spring.io/spring-modulith/reference/verification.html（`verify()` 校验：模块间无环、只能经 API 包访问、只允许显式声明的依赖） | 本仓「模块契约 + 薄内核 + fail closed」的形态，是否仍属于模块化单体的主流做法，而不是必须演进成服务拆分或运行时插件的信号？ | 只用于确认「单部署单元 + 显式模块边界 + 依赖校验」在业界是否常规；不得据本行认定本仓模块划分已达标或不合格，更不得作为拆分成多个服务、引入运行时插件市场的依据。 | 核验处 `apps/api/kernel/module.go`（API 版本、Resolve 的依赖/冲突校验）、`apps/api/kernel/provider.go`（Registrar 发布路径）：是否只有一个发布路径、是否存在跨模块直接引用 internal 包；可对齐 R2 矩阵行 01/02/03。 |

| 1.3 | 装配图在启动阶段被显式校验（缺依赖、冲突、作用域不匹配即失败退出），而不是等到首次调用才暴露装配错误。 | ① pkg.go.dev · go.uber.org/fx — https://pkg.go.dev/go.uber.org/fx（`ValidateApp`："validates that supplied graph would run and is not missing any dependencies"，不执行实际构造）② Microsoft Learn · .NET Generic Host — https://learn.microsoft.com/en-us/dotnet/core/extensions/generic-host（`CreateApplicationBuilder` 在 Development 环境启用 scope validation 与 dependency validation） | 「Resolve 阶段校验依赖与冲突、校验后整体发布、失败即 fail closed」是否属于业界常规的启动期装配校验，而不是过度防御？ | 只用于确认「启动期校验装配图」是常规做法；不得反推本仓校验已完备或需要新增校验框架，也不得据此改动内核契约或错误语义。 | 核验处 `apps/api/kernel/module.go`（Resolve 的冲突/缺失依赖处理）、`apps/api/kernel/provider.go`（校验后整体发布的顺序语义）：确认「校验先于发布」是否有可核对的测试支撑（如 dual-profile 契约矩阵测试）。 |

## 2. 基础设施端口（infrastructure ports with in-memory defaults）

| # | 业界常见做法（industry common practice） | 代表参照（representative references） | 可对照的本仓问题（the repo question this row can judge） | 不推翻项（what this row must NOT be used to overturn） | 核验提示（verification hint） |
|---|---|---|---|---|---|
| 2.1 | 每个外部依赖（存储、缓存、限流、消息、邮件等）以端口接口表达，内存/回环适配器是该端口的常规实现之一，用于脱离真实基础设施运行、测试与本地开发。 | ① Alistair Cockburn · Hexagonal architecture（2005 原文） — https://alistair.cockburn.us/hexagonal-architecture/（端口 + 适配器；适配器包含 "an adapter to a 'mock' database, one that sits in memory and doesn't depend on the presence of the real database at all"）② Microsoft Learn · Common web application architectures — https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures（Application Core 定义接口、Infrastructure 实现；测试期以 fake 实现替换层） | 「内核定义端口 + 内存实现为默认」在 ports & adapters 语境下是否属于常规落法，而不是「外部集成尚未完成」的替代表述？ | 只用于分类端口形态；不得据此认定每个端口都必须配内存实现，也不得把「内存实现是惯例」当作阻止未来真实适配器另立评估的理由。 | 核验处 `apps/api/kernel/`（store / cache / ratelimit / eventbus / mail / objectstore / telegram 等端口声明）与 `apps/api/internal/*/`（内存实现）：逐端口记录「有端口无实现」「有实现无消费者」两类事实，供 R3 分类（对照 R2 矩阵行 06/07/08/09）。 |
| 2.2 | 外部后端按「可挂载资源」处理：本地实现与第三方服务在代码中不做区分，只有配置里的资源句柄/凭据不同，替换实现不需要改代码。 | ① The Twelve-Factor App · IV. Backing services — https://12factor.net/backing-services（"The code for a twelve-factor app makes no distinction between local and third party services"；替换本地/第三方服务只需改 config 中的资源句柄，无需改代码） | 把 Redis/MQ 这类外部后端留成「配置 + 接缝切换」而不是编入业务代码，是否符合常规做法？ | 不得据此认为本仓现在就该接入 Redis/MQ/K8s（触发条件未满足时保持 gated），也不得把「可挂载资源」当作外部适配器已实现或已验证的证据。 | 核验处 `apps/api/kernel/cache.go`、`apps/api/kernel/eventbus.go` 等端口签名：是否只暴露标准库/自有类型（对照 R2 矩阵行 17 的供应商泄漏抽检），以及配置层/接缝文档是否给出切换入口（cache seam 文档 §2.6 现状另见 G-003）。 |
| 2.3 | 缓存先做进程内私有缓存；只有需要跨实例一致视图或可扩展性时才引入共享缓存，且共享缓存不得作为权威数据存储，共享缓存不可用时应能回退到源存储继续服务。 | ① Microsoft Learn · Caching guidance（Azure Architecture Center） — https://learn.microsoft.com/en-us/azure/architecture/best-practices/caching（private in-memory cache 与 shared cache 的取舍；"don't use the cache as the authoritative store of critical information"；共享缓存不可用时应用应能继续运行并回退到原数据存储） | 「缓存默认内存实现、Redis 作为未实现接缝（触发条件满足再评估）」在什么条件下才算偏离常规？ | 不得据此要求立刻实现 Redis 适配器；也不得把进程内缓存的多实例不一致语义直接判为缺陷，或以此要求改成共享缓存。 | 核验处 `apps/api/internal/cache/memory.go`（有界容量、拷贝语义）与 `apps/api/kernel/cache.go`（namespace/key/expiry 约束）：确认文档是否把内存实现描述为唯一形态；G-003 的端口描述滞后属文档事实，另行分类。 |
| 2.4 | Go 生态里接口按「消费方需要」定义：不为假想的实现或 mock 在实现方定义接口，也不在出现真实用例之前预先定义接口。 | ① Go Wiki · Go Code Review Comments（"Interfaces" 节） — https://go.dev/wiki/CodeReviewComments（"Go interfaces generally belong in the package that uses values of the interface type"；"Do not define interfaces on the implementor side of an API 'for mocking'"；"Do not define interfaces before they are used"） | 已经存在但尚无外部实现的接缝（如 Redis 替换路径）在该惯例下，应判为「提前抽象」还是「已冻结的边界」？ | 本行只澄清「何时该定义接口」的惯例；不得用来主张删除既有内核端口、把已冻结的接缝判为违规，或据此重开端口公开语义。 | 核验提示：分别记录两类事实——既有端口是否已被消费方（modules/composition）真实使用；接缝文档描述的替换路径是否已有明确触发条件（RT-Q03/Q05、A3 等）。两者不要合并成结论。 |

## 3. Schema 驱动 Admin（schema/protocol-driven admin UI：contributions, not hand-registration）

| # | 业界常见做法（industry common practice） | 代表参照（representative references） | 可对照的本仓问题（the repo question this row can judge） | 不推翻项（what this row must NOT be used to overturn） | 核验提示（verification hint） |
|---|---|---|---|---|---|
| 3.1 | 用声明式 schema（如 JSON Schema）描述数据结构与约束，由通用渲染器据此生成表单/页面，schema 同时承担校验与文档职责，只把外观差异交给额外的 UI 描述。 | ① JSON Schema · What is JSON Schema? — https://json-schema.org/overview/what-is-jsonschema（"JSON Schema is a declarative language for defining structure and constraints for JSON data"；支持机器/人类可读文档与校验）② react-jsonschema-form documentation — https://rjsf-team.github.io/react-jsonschema-form/docs/（"automatically generate a React form based on a JSON Schema"；`uiSchema` 仅做外观定制） | 「页面由 schema 描述、由宿主渲染」是否属于 admin/后台界面的主流做法，还是本仓自创形态？ | 不得据此把「schema 驱动」扩大解释为必须实现通用低代码/表单设计器，也不得要求把所有手写页面改造成 schema 渲染。 | 核验处 `apps/web/src/protocol/load-page.ts`（schemaUrl 加载路径）与自定义渲染组件注册入口：记录「哪些页面确实由 schema 描述、哪些是手写组件」，不要用本行推断未实现的渲染能力。 |
| 3.2 | 管理界面的页面与导航由各插件/模块以扩展点贡献，宿主自动发现并聚合，应用侧不做中心手写注册表；后端只负责把各功能接线成一个部署单元。 | ① Backstage · Common Extension Blueprints — https://backstage.io/docs/frontend-system/building-plugins/common-extension-blueprints/（Page/SubPage/NavContent 等 blueprint："Nav items are auto-discovered from page extensions"）② Django · The Django admin site — https://docs.djangoproject.com/en/stable/ref/contrib/admin/（admin 依据模型元数据提供界面；`autodiscover()` 在启动时为每个 installed app 导入 `admin` 模块完成注册）③ Backstage · Backend System Architecture — https://backstage.io/docs/backend-system/architecture/index/（backend 本身无功能，"simply responsible for wiring things together"；功能由 plugins/modules 提供） | 「贡献聚合 + 分组归一化 + 冲突拒绝」这一 manifest 形态是否属于贡献式（而非中心注册式）admin 的常规做法？ | 不得据此要求引入第三方/运行时插件市场或动态装载；也不得把「应用侧仍保留自定义渲染组件注册」直接判为偏离惯例。 | 核验处 `apps/api/internal/manifest/manifest.go`（贡献投影/分组/冲突拒绝）、`apps/web/src/app/navigation.ts` 与 `apps/web/src/app/App.tsx`：是否存在第二套中心业务导航表（对照 R2 矩阵行 15/W1）。 |

## 4. 同进程基座（same-process foundation）

| # | 业界常见做法（industry common practice） | 代表参照（representative references） | 可对照的本仓问题（the repo question this row can judge） | 不推翻项（what this row must NOT be used to overturn） | 核验提示（verification hint） |
|---|---|---|---|---|---|
| 4.1 | 默认从单体起步：只有当系统复杂度（规模、团队、独立演进/伸缩需求）确实超出单体管理能力时才拆服务，分布式带来的额外成本即 microservice premium。 | ① Martin Fowler · bliki: MonolithFirst — https://martinfowler.com/bliki/MonolithFirst.html（成功案例多始于单体再拆分；从一开始就做微服务常出问题）；② Martin Fowler · bliki: Microservice Premium — https://martinfowler.com/bliki/MicroservicePremium.html（"don't even consider microservices unless you have a system that's too complex to manage as a monolith"；多数系统应以单体构建，但要注意单体内部模块化） | 「同进程基座、把更多产品模块跑在同一进程」这一取向是否属于业界默认选择？ | 只用于分类默认取向；不得据此宣布永不拆分，也不得把本行当作拒绝未来任何服务化评估的永久结论。 | 核验提示：记录当前部署单元事实（API 进程数、Web 与 API 的边界、是否有第二个服务进程），并单列「同一组合根下运行的产品模块清单」；不要用本行推断未来路线图。 |
| 4.2 | 同一部署单元内运行多个功能模块时，各模块共享宿主提供的基础服务（配置、日志、数据访问、生命周期），并作为整体部署与伸缩，而不是每个模块一个进程。 | ① Microsoft Learn · Common web application architectures — https://learn.microsoft.com/en-us/dotnet/architecture/modern-web-apps-azure/common-web-application-architectures（单体容器化部署："Externally, it's a single container with a single process, single web application, or single service"；整体复制即可伸缩；拆分只有在能独立交付功能切片时才值得）② Backstage · Backend System Architecture — https://backstage.io/docs/backend-system/architecture/index/（backend 是部署单元并只负责接线，"You can have all features in a single one"；module 必须与所属 plugin 部署在同一 backend 实例、共享 services，仅通过 extension points 通信） | 「多产品模块同进程、共享端口与生命周期」是否属于常规基座形态，而不是必须拆成多个服务才算完整？ | 不得把「同进程」绝对化为不可变更的架构承诺；也不得据此否决未来按模块边界做拆分评估的需求。本行仅作分类输入。 | 核验处 `apps/api/kernel/lifecycle.go`（启动/停止拓扑）、`apps/api/internal/composition/composition.go`（共享单例接线）：确认是否存在第二个进程边界（独立 worker/服务）或按模块独立部署的配置；对照 R2 矩阵行 11/13。 |
| 4.3 | 模块间的主要交互走进程内事件发布/订阅；只有在明确需要跨进程或对接外部系统时才把事件外部化，且外部化需要显式标注并引入对应 broker 依赖。 | ① Spring Modulith Reference · Working with Application Events — https://docs.spring.io/spring-modulith/reference/events.html（"their primary means of interaction should be event publication and consumption"；外部化需事件标注 + 引入 broker 专用 artifact，默认留在进程内） | 进程内 EventBus 作为默认运输、不提供跨进程可靠消息，这一形态是否属于同进程基座的常规做法（而非必须换成 broker）？ | 不得据此把进程内 EventBus 扩写成事务持久化/可靠消息能力；也不得用本行否决未来按触发条件引入 broker 的评估。 | 核验处 `apps/api/kernel/eventbus.go`（主题/背压契约）与 `apps/api/internal/eventbus/memory.go`：确认文档与代码是否把进程内运输描述为可替换 broker，或已明确其不跨进程边界（对照 R2 矩阵行 08/12）。 |
